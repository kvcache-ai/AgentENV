Gateway and Scheduler Configuration

The Gateway and Scheduler load JSON configuration through their -config command-line argument. The same configuration format is used by these multi-node deployments:

DeploymentConfiguration files
Docker Composedeploy/docker/config/default.json, shared by both services.
Static Multi-Node/etc/agentenv/control-plane.json, shared by both services in the guide.
Kubernetesdeploy/k8s/base/config/scheduler.json and deploy/k8s/base/config/gateway.json, supplied through ConfigMaps.

Configuration is loaded in this order, with later values overriding earlier ones:

  1. Built-in defaults.
  2. The JSON file selected by -config.
  3. Supported environment variables in the service process.

The Default column lists built-in values, which may differ from values explicitly set in deployment examples. Configuration is read at startup; restart the affected services after applying changes using the relevant deployment guide. Runtime-node TOML settings are documented separately in the Runtime Node Configuration.

scheduler.discovery

scheduler.discovery.mode selects how the Scheduler discovers runtime nodes:

  • static (the default) uses the node list in scheduler.nodes.

Each scheduler.nodes entry accepts:

FieldMeaning
idRuntime node ID, matching that runtime’s AENV_NODE_ID.
endpointRuntime API URL reachable from the Gateway, such as http://agentenv-a:8000.

Static mode requires a nonempty node list and nonempty IDs and endpoints. If nodes is omitted entirely, the built-in list contains local-node at http://127.0.0.1:8000.

For example, merge the following fields into the existing scheduler object to use the two runtime services in the Docker Compose deployment:

{
  "nodes": [
    {
      "id": "node-a",
      "endpoint": "http://agentenv-a:8000"
    },
    {
      "id": "node-b",
      "endpoint": "http://agentenv-b:8000"
    }
  ],
  "discovery": {
    "mode": "static"
  }
}
  • kubernetes uses scheduler.discovery.kubernetes to watch a Service’s EndpointSlices.

The following fields belong under scheduler.discovery.kubernetes and are used only in Kubernetes mode:

FieldDefaultMeaning
namespace""Service namespace; required in Kubernetes mode.
service_name""Service whose EndpointSlices supply runtime nodes; required.
port0EndpointSlice port to match and use in runtime URLs; must be positive.
scheme"http"Scheme used to construct runtime URLs.
ignore_pod_selector""Optional Kubernetes label selector; matching Pods are excluded from discovery entirely.
no_schedule_pod_selector""Optional label selector; matching Pods are retained as lingering nodes for existing routing but excluded from new placement.

Nonempty selectors must be valid Kubernetes label selectors.

For example, merge the following field into the existing scheduler object for the Service agentenv-nodes in namespace agentenv-system:

{
  "discovery": {
    "mode": "kubernetes",
    "kubernetes": {
      "namespace": "agentenv-system",
      "service_name": "agentenv-nodes",
      "port": 8000,
      "scheme": "http"
    }
  }
}

scheduler.node_resource_limit

For a new scheduling request, the Scheduler takes discovered, non-lingering nodes, filters them against scheduler.node_resource_limit, then selects one using round robin or random selection.

Every resource-limit field is optional. An omitted field imposes no limit.

Field under scheduler.node_resource_limitNode metric compared with the threshold
max_sandbox_countActive sandbox count, excluding paused sandboxes.
max_sandbox_starting_countNumber of sandboxes currently starting.
max_cpu_used_percentCPU usage percentage reported in the heartbeat.
max_cpu_allocated_percentAllocated CPU / total node CPU × 100.
max_memory_used_percentUsed memory / total node memory × 100.
max_memory_allocated_percentAllocated memory / total node memory × 100.
max_sandbox_count_including_pausedActive plus paused sandbox count.
max_allocated_cpu_including_pausedActive plus paused CPU allocations, in CPU units, not percent.
max_allocated_memory_bytes_including_pausedActive plus paused memory allocations, in bytes.

Enabling TLS switches the main listener to HTTPS. It does not also start an HTTP listener or an HTTP-to-HTTPS redirect.

For an existing certificate, add this object inside gateway:

"tls": {
  "mode": "manual",
  "cert_file": "/etc/agentenv/tls/fullchain.pem",
  "key_file": "/etc/agentenv/tls/privkey.pem"
}

For ACME with a wildcard sandbox domain, a Cloudflare example is:

"tls": {
  "mode": "acme",
  "domains": ["api.example.com", "*.sandbox.example.com"],
  "storage_dir": "/var/lib/agentenv/tls",
  "email": "operator@example.com",
  "challenge": "dns-01",
  "dns_provider": "cloudflare",
  "dns_config": {
    "api_token": "<cloudflare-api-token>"
  }
}

IP certificates require TLS-ALPN-01, allow at most one IP per listener, and reject private or special-purpose IPs. TLS-ALPN-01 must not include dns_provider or dns_config, and public TCP port 443 must reach the Gateway TLS listener for validation.

Wildcard certificates require DNS-01. When challenge is set to dns-01, configure dns_provider and its corresponding dns_config object. Supported providers and their configuration fields are listed below:

ProviderFields
cloudflareRequired api_token; optional zone_token for separate Zone-read access.
alidnsRequired access_key_id, access_key_secret; optional region_id, security_token.
tencentcloudRequired SecretId, SecretKey; optional SessionToken, Region. These are the field names exposed by the current dependency.
route53Optional access_key_id and secret_access_key, supplied together or both omitted to use the AWS credential chain; also session_token, region, profile, and hosted_zone_id. Additional options: max_retries (retry count), route53_max_wait (maximum internal AWS synchronization wait), wait_for_route53_sync (wait for that synchronization), and skip_route53_sync_on_delete (skip it on deletion). route53_max_wait takes an integer number of nanoseconds, not a duration string such as "30s".

Unknown provider fields are rejected.

Example configuration

This example uses the two runtime nodes in the Docker Compose deployment, static discovery, round-robin placement, and an HTTP Gateway.

{
  "log_level": "info",
  "log_format": "json",
  "scheduler": {
    "grpc_listen_addr": ":9090",
    "strategy": "round_robin",
    "discovery": {
      "mode": "static"
    },
    "nodes": [
      {
        "id": "node-a",
        "endpoint": "http://agentenv-a:8000"
      },
      {
        "id": "node-b",
        "endpoint": "http://agentenv-b:8000"
      }
    ],
    "node_resource_limit": {
      "max_cpu_used_percent": 85,
      "max_memory_used_percent": 90
    }
  },
  "gateway": {
    "http_listen_addr": ":8080",
    "scheduler_addr": "scheduler:9090",
    "request_timeout": "90s"
  }
}
